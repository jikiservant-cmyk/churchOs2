## The two defects, restated for your actual data

### 1. The columns do not exist → "Church not found."

`lib/attendance-actions.ts` selects `passkey_hash` and `passkey_version`.
Neither column exists, so PostgREST answers `42703`, the row comes back empty,
and the portal reports a church that plainly exists as missing.

**Fixed in code:** `42703` now produces
*"Usher login is misconfigured: this database is missing required columns. Ask an
administrator to run migration 011."*

### 2. Sixteen churches have no passkey to enter

The old rotation path wrote hash-only — `updateChurchPasskey` set
`passkey = null` alongside the hash — while the admin screen renders `passkey`.
Every church that ever rotated lost its readable code. Combined with the absent
`passkey_hash` column, those rows hold **no usable credential of any kind**.

**Fixed in code:** rotation now keeps the readable value, and login reports
*"No usher passkey is configured for this church yet…"* instead of
*"Invalid passkey"*, so the next person to try knows it is not their typing.

## Migration review (as requested)

Both files were executed against a real PostgreSQL 16 (PGlite) on a table shaped
like your deployment — `passkey` nullable, the other three columns absent, 18
rows with 16 NULLs. `npm run test:migrations` → **19/19 checks pass.**

### `011_usher_passkey_columns.sql` — structural only

* **Additive only.** Three `ADD COLUMN IF NOT EXISTS`. No `DROP`, no `RENAME`,
  no data rewrite.
* **The statement that cleared hashes is gone.** I removed it. It was pointless
  here — on a database without the column, every added column starts NULL, so
  there is nothing to clear — and it was the one destructive statement in the
  file. Verified by test: *"011 invents no hashes"* and *"011 leaves existing
  readable passkey untouched"*.
* **No credentials in the log.** The old version printed every passkey via
  `RAISE NOTICE`, which would have copied 18 live codes into your psql
  transcript and any log shipping on top of it. The report now emits **counts
  only**; a test asserts every `RAISE` argument is a count variable.
* **Does not invalidate live sessions.** `passkey_version` is set to 1 only
  where it is NULL, which is what already-issued usher JWTs assume.
* Idempotent — re-running is a no-op (tested).

### `012_usher_passkey_backfill.sql` — issues a passkey where none exists

This is the file that actually unblocks the 16 churches, and it is deliberately
**separate** so you can apply 011 alone and inspect first.

* `UPDATE … WHERE coalesce(trim(passkey), '') = ''` — touches only rows with no
  readable code. **Nothing else.**
* Generates `upper(substr(replace(gen_random_uuid()::text,'-',''),1,10))` —
  10 hex characters, matches the portal validator `^[A-Za-z0-9_-]{6,32}$`, and
  needs no extension. 500 generated values: zero invalid.
* **Does not bump `passkey_version`**, so nobody is logged out.
* **Does not print the codes.** Retrieve them yourself afterwards:
  ```sql
  SELECT slug, passkey FROM church.churches ORDER BY slug;
  ```
  That keeps 18 live credentials out of logs and migration history.
* Idempotent — a second run does not rotate the codes again (tested).

**Sample run, on the synthetic 18-row table:**

```
PASS  012 leaves no church without a credential — 0 remaining
PASS  012 codes all satisfy the portal validator — 0 invalid
PASS  012 generates distinct codes — 18/18 distinct
PASS  012 does not rewrite existing passkeys — 482913
PASS  012 does not bump passkey_version (live sessions survive)
```

### Deploy order

```bash
# 1. staging first
psql "$STAGING_DATABASE_URL" -v ON_ERROR_STOP=1 -f migrations/011_usher_passkey_columns.sql
psql "$STAGING_DATABASE_URL" -v ON_ERROR_STOP=1 -f migrations/012_usher_passkey_backfill.sql
psql "$STAGING_DATABASE_URL" -c "SELECT slug, passkey FROM church.churches ORDER BY slug;"
# 2. log in to each portal with its code
# 3. only then production
```

Both files are wrapped in `BEGIN; … COMMIT;`, so 011 fails and rolls back
cleanly if the `church` schema or table is missing.

## Still outstanding

1. **`provision_church_v3` is only in the database.** Dump it into the repo so
   the schema is reproducible:
   ```sql
   SELECT pg_get_functiondef(p.oid)
   FROM   pg_proc p JOIN pg_namespace n ON n.oid = p.pronamespace
   WHERE  n.nspname = 'public' AND p.proname = 'provision_church_v3';
   ```
   Its body also decides what a *new* church's passkey looks like, so the repo
   is currently guessing.
2. **The repo's `passkey` column is `NOT NULL`, but your live table holds NULLs.**
   Another sign the deployed table does not match `supabase-schema.sql`. I left
   the constraint alone — it will surface this class of bug loudly — but the
   drift should be reconciled deliberately, not silently.
3. **16 NULL passkeys mean nobody has been able to run check-in** for those
   churches. Worth confirming none of them had an active service expecting
   attendance records during the outage.

## Verify after deploying

```sql
SELECT count(*) FILTER (WHERE coalesce(trim(passkey),'') = '') AS still_missing,
       count(*) FILTER (WHERE passkey ~ '^[0-9A-F]{10}$')      AS generated,
       count(*)                                                AS total
FROM   church.churches;
```

`still_missing` must be `0`. Then open `/<slug>/usher` and enter that church's
code. Error messages now distinguish every case:

| Message | Meaning |
|---|---|
| `Church not found.` | wrong slug in the URL |
| `…missing required columns…` | 011 not applied |
| `No usher passkey is configured…` | 012 not applied and the row is empty |
| `Invalid passkey format.` | not 6–32 chars, or outside `A-Z a-z 0-9 _ -` |
| `Invalid passkey. Please check…` | genuinely wrong code |
